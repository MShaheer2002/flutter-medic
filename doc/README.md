## Where things stand right now

**Phase 1 is complete** (orchestration server, tool routing, device detection, launch/interact/observe, console log capture — all built and verified against a real device; see 003–009). **Phase 2's core architecture is proven**, not just built: given only a plain-language goal, an AI agent used the granular tools (`launch_app`/`observe`/`enter_text`/`tap`) to explore `crash_demo_app`, reasoned entirely from tool-observed evidence (recognized a login form, filled it in, then read a real crash out of `observe`'s output), and hands off to `reproduce` for a reproduced, confirmed verdict against the same running app, no relaunch needed. Zero pre-written steps, zero prior-knowledge shortcuts in the reasoning chain (012).

The orchestrator exposes two distinct modes: `investigate` (self-contained — give it exact steps and an expected element, it launches, reproduces 3x, and closes) and now **sixteen** granular tools — `launch_app`, `tap`, `enter_text`, `observe`, `hot_restart`, `hot_reload`, `reproduce`, `close_app`, plus the gesture/keyboard/inspection set from 014 (`double_tap`, `long_press`, `secondary_tap`, `swipe`, `pinch_zoom`, `scroll_to`, `press_back_button`, `press_key`, `take_screenshots`, `get_logs`) — that hold session state across calls so a calling agent can explore a screen, decide what it means, verify what it found against the same running app, and close when actually done. `observe` returns raw evidence with no anomaly rules applied; judgment is the calling agent's job. The reproduction loop itself (`reproduction.ts`) is shared between `investigate` and `reproduce`.

**Network evidence now captured and live-verified (015)**: `observe`/`reproduce`/`investigate` all include real HTTP request/response data (`networkActivity`, via the Dart VM service's HTTP profiling) alongside runtime errors and native logs — root-caused why this had never worked (only instruments a real Flutter-embedded isolate, never a bare Dart CLI process) rather than accepting the earlier apparent dead end. `killer_demo_app` now makes a real, self-contained HTTP call instead of an in-memory fake, and a live run through the real MCP tool confirmed all 3 reproductions carry a genuine `GET /tasks → 200 OK` profile alongside the correctly-firing `expected-element-missing` signal — the spec's own original worked example (§6/§8.3), confirmed end to end. This is evidence capture, not a new detection rule — matching the existing "raw evidence, calling agent judges" design, since generically deciding "does response count match rendered count" is real judgment, not a safe hardcoded rule across arbitrary apps.

**Tier 2 (baseline-diff) built and live-verified (016)**: a new `baseline-drift` signal flags anything different from a previously banked known-good run of the same app+steps, not just what a tier-1 rule was told to check for — first-run-wins baselines saved to `~/.flutter-medic/baselines/`. The rule itself works correctly. This closes out Phase 2's anomaly-detection scope: tier 1 (007/009), tier 2 (016), and tier 3 (already informally realized by the granular-tool architecture itself — the calling agent's own reasoning over raw evidence, 012) are all now in place.

**Known open issue, found via 016's live testing**: right after `hot_restart`, evidence capture (`interactiveElements`) can reflect a screen stuck mid-render rather than the real settled state — confirmed via screenshot (AppBar correctly shows the destination screen's title, but the body is blank, matching none of that screen's real render states) and ruled out as a timing race (a poll-until-stable wait, `waitForStableUi` in `reproduction.ts`, proves the bad reading is stable, not transient). Root cause not found — worth a focused investigation (hypotheses: stale Marionette semantics-tree binding, or Flutter ticker/animation state not resetting on hot restart). Affects any rule reading `interactiveElements` after a `hot_restart`, not just tier-2.

**Confirmed gap, not a guess**: Marionette has zero device-sensor simulation (no accelerometer/GPS/orientation/battery) — searched its entire source, no matches. Nothing else explored so far (Dart MCP, Patrol) covers this either.

**Confirmed across two demo apps, three distinct bug shapes**: `killer_demo_app`'s silent state bug (caught only by `expected-element-missing`), a fire-and-forget async exception (caught only by `native-log-exception`, 007/009), and `crash_demo_app`'s synchronous build-crash (caught by `runtime-exception`, the primary VM-service rule, proven for the first time against a real, non-injected bug — 012).

**Confirmed in Phase 0**: OBSERVE → ACT → OBSERVE works via Marionette on two different physical devices. MCP server scope (`local` vs `project`) matters for onboarding UX. Patrol MCP does not work reliably in this environment — root cause not found despite an exhaustive investigation (003/004) — not a blocker; the core loop needs only Marionette + Dart MCP.

**Next up (not yet decided)**: `flutter-medic init` (§14), log correlation and structured report generation to round out Phase 3, or moving toward CI/headless usage (Phase 6).
